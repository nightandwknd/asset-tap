# Browser (wasm32) feasibility: 3D viewer and humanoid rig

Spike branch: `spike/browser-viewer-feasibility-20261107`. Harness, commands and
the browser checklist: [README.md](README.md). Raw outputs: [results/](results/).

**Browser status: UNVERIFIED.** No browser was started by the author of this
document. Compilation, a wasm VM under Node, and unit tests were run. Nothing
below asserts a browser outcome.

### Reported browser attempt (externally supplied, not measured here)

A separate party reported trying the harness URL
(`http://127.0.0.1:8137/?glb=fixtures/mannequin_g4_baked.glb`) twice, plus the
bare localhost address once, in Chrome 156.0.8078.47. All three attempts showed
`net::ERR_CONNECTION_REFUSED` and the app did not load. They also reported that a
separate shell `curl` against the same address returned HTTP 200.

These are second-hand observations. I did not reproduce them and did no network
or browser diagnosis, so **no cause is inferred**. As a result, still not
verified in any browser: page load, WebGL2 context, rendering, PBR/lighting,
animation playback, frame rate, GPU behavior and browser memory. Another
desktop verification attempt is pending. **Browser rendering remains an open
gate; the verdict stays a conditional go.**

## Verdict: conditional go

- **Compute (rig, bind, bake, CPU skinning): go.** The real rig source compiles
  for `wasm32-unknown-unknown` and `wasm32-wasip1`, and runs single-threaded in a
  wasm VM (Node/V8) with sub-second bind on a 301k-vertex mesh. The blocker is
  API shape (paths and `std::fs`), not the algorithms.
- **Rendering: go, gated on browser verification.** The real `three-d` viewer
  type-checks and builds for wasm32 with exactly two small source adaptations.
  Whether it renders (WebGL2, environment lighting, framebuffer blit) is not
  known.
- **Do not extract crates yet.** Step 0 below (browser verification of this
  harness) gates the viewer half. The rig half can start independently.

### The exact viewer adaptations

`web/build.rs` copies `model.rs` to the build output and applies, and nothing
else (each target must match exactly once or the build fails):

0. 4 leading `//!` lines become `//`. Comment-only; inner docs are illegal under `include!`.
1. **Patch 1.** `three_d_asset::io::load(&[&temp_path])` becomes an empty
   `RawAssets`. That function does not exist on wasm32 (the crate gates it
   `cfg(not(target_arch = "wasm32"))`). The path-based `load_cpu_model_data` is
   therefore dead on the web.
2. **Patch 2.** `SharedModelViewer = Arc<Mutex<ModelViewer>>` becomes
   `Arc<Mutex<SendWrapper<ModelViewer>>>`. `egui_glow::CallbackFn` requires
   `Send + Sync`, and glow's WebGL `Context` holds `RefCell`s, so `ModelViewer`
   is not `Send` on the web.

Unpatched, the viewer fails to compile for wasm32 with exactly those two
errors. A comment in `build.rs` previously said "the only change" while the file
also applied the two patches; that contradiction is fixed. The served bundle was
built before that comment-only edit; no code changed.

## Evidence

### Environment and method

- Host: Intel Xeon (model string not reported more specifically), 8 logical
  cores, 16,002 MiB RAM, Linux 6.12. No GPU was involved; nothing was rendered.
- The sandbox `rustc` was 1.85.1 with no wasm target, and the locked
  dependencies need 1.88 or newer. The repo's pinned **1.97.1** and its
  `wasm32-unknown-unknown` / `wasm32-wasip1` std were installed from the
  official standalone tarballs (SHA-256 files checked) into a scratch prefix.
  Nothing system-wide changed.
- Runtime for wasm numbers: Node v24.22.1, V8 13.6.233.17-node.58. This is a
  wasm VM, **not a browser**; browser JIT tiers, memory caps and main-thread
  scheduling can differ.
- Each configuration ran 3 times in fresh processes; tables show the median with
  `[min-max]`. All probes use `--release`.
- Fixture sizes: `g4` 2,400 verts / 3,072 tris (116 KB); `g20` 42,336 verts /
  76,800 tris (2.3 MB); `g55` 301,056 verts / 580,800 tris (16.6 MB). `g55` is
  chosen to match the vertex class of the showcase model (286k verts, 500k tris)
  without using it.
- "Bind" is `fit_mesh` (landmarks, fit, weights, skinned rest). "Bake" is
  `apply_clip` of `Walk_Loop` onto the fitted rest and includes reading the 7.6 MB
  `ual1` pack. "Skin" is one CPU `SkinnedClip::sample_positions_into` pass.

### Unit tests

`cargo test -p asset-tap-core-shim` runs the **real** rig tests natively:
**103 passed, 2 failed** ([results/shim-rig-unit-tests.txt](results/shim-rig-unit-tests.txt)).
Both failures are caused by a stand-in, not by the rig:

- `rig::pack::tests::a_zip_without_a_library_reports_that_and_not_a_parse_error`:
  expected `NoLibrary`, got `Install("spike stand-in: zip extraction not implemented")`.
- `rig::pack::tests::install_from_a_zip_picks_the_library_over_the_mannequin`:
  `install from zip: Install("spike stand-in: zip extraction not implemented")`.

Both exercise zip install through `bundle::extract_zip_to_dir`, which the shim
stubs. (Five fetch tests failed earlier on an empty `CLIP_PACKS_SIZE_LABEL`
stand-in constant; they passed after it was set to the real value, `"15 MB"`.)
Not run: the desktop workspace's `make ci`, `make test`, clippy and fmt (the
workspace cannot build in this sandbox, see above). The spike is outside the root
workspace, so those jobs do not cover it. The 105 tests also do not run on
wasm32; no wasm test runner was set up.

### Bind, bake and skinning timings

Native (release; `RAYON_NUM_THREADS=1` vs default 8 threads) and the same real
rig source as `wasm32-wasip1` under Node, single rayon thread. Raw files:
[native](results/native-timings.txt), [wasi](results/wasm32-wasip1-node-timings.txt).

| Fixture | Native 1 thread: bind / bake / skin | Native 8 threads: bind / bake / skin | wasm VM, 1 thread: bind / bake / skin |
| ------- | ----------------------------------- | ------------------------------------ | ------------------------------------- |
| g4      | 5.9 / 44.3 ms / 0.03 ms/frame       | 4.4 / 43.0 ms / 0.04 ms/frame        | 20.8 / 47.9 ms / 0.05 ms/frame        |
| g20     | 80.8 / 45.7 ms / 0.33 ms/frame      | 45.1 / 48.5 ms / 0.10 ms/frame       | 114.1 / 54.2 ms / 0.72 ms/frame       |
| g55     | 599.9 / 182.6 ms / 2.38 ms/frame    | 306.5 / 166.7 ms / 0.39 ms/frame     | 666.7 / 152.3 ms / 4.85 ms/frame      |

Ranges for g55 bind: native 1T `[599.0-622.4]`, native 8T `[300.8-351.1]`, wasm
`[632.5-779.7]` ms. Small-fixture bake is about 45 ms regardless of mesh size,
which suggests a fixed cost (reading the pack). That is an inference; it was not
separately timed.

Skinning on the **browser target itself** (`wasm32-unknown-unknown`, in-memory
bytes via the real `SkinnedClip`, Node-hosted;
[results](results/wasm32-unknown-unknown-node-probe.txt)): 0.043 ms/frame (g4),
0.664 (g20), 4.695 (g55). Parse time was 1-7 ms (g4), 4-8 (g20), 20-44 (g55) but
used `Date.now()` (about 1 ms resolution), so only the g55 figure is meaningful.

#### Memory: corrected labels

Two different quantities were measured and an earlier label conflated them.

- **Native** column: `VmHWM`, the kernel's peak resident set (RSS) for the whole
  process. Medians: 20 MiB (g4), 31 MiB (g20), 176 MiB (g55).
- **Wasm** runs: the number is **wasm linear-memory size read at exit** (pages x
  64 KiB). It is **not RSS and not a peak or high-water measurement of live data**.
  The original output line said "peak RSS VmHWM=... (wasm linear memory)"; that
  label was wrong. Original lines are preserved; correction notes were added at
  the top of the two wasm result files, and the probe source now prints the
  correct label (a re-run printed the identical 17600 kB for g4, so only the
  label changed). Values: wasip1 17 / 28 / 196 MiB (g4 / g20 / g55); the
  `wasm32-unknown-unknown` skinning-only probe ended at 2.1 / 13.8 / 91.2 MiB.
- The two kinds of number **must not be compared** with each other. Browser tab
  memory was not measured.

#### Observations on these numbers

- Wasm-VM single-thread bind vs native single-thread (medians): about 3.5x
  slower at g4 (20.8 vs 5.9 ms), 1.4x at g20 (114.1 vs 80.8 ms), 1.1x at g55
  (666.7 vs 599.9 ms); the g55 ranges do not overlap (wasm `[632.5-779.7]`,
  native `[599.0-622.4]`). Bake at g55 was faster on wasm (152.3 vs 182.6 ms);
  I did not investigate why (the two runs differ in file I/O layer and
  allocator), so treat bake as roughly comparable, not faster.
- Wasm skinning is about 2x native single-thread (4.85 vs 2.38 ms/frame at
  g55; 0.72 vs 0.33 at g20).
- Native multithreading helps: bind about 1.8x at g20 and 2.0x at g55; skin about
  6x at g55 (2.38 to 0.39 ms/frame). A single-thread browser forgoes that.
- At 301k vertices, one single-thread wasm skinning pass is about 4.7 ms, about
  28% of a 16.7 ms frame before upload and draw. Smaller meshes are
  comfortable. Whether 60 fps holds at g55 in a browser is unknown.
- Outputs are not byte-identical across targets: g4 rigged rest is 190,932 B on
  wasm and 190,928 B native (baked 316,576 vs 316,572). Cause not investigated;
  the repo already documents that `serde_json` `f32` output is not a fixed point.
  Golden tests must not compare bytes across targets.

## Blockers and platform differences

**Native dependencies in `asset-tap-core` that block wasm32:** `tokio` with
`full` (pulls `mio` networking), `reqwest` (native-TLS), `dirs`, `tempfile` and
`std::fs` use, and the pack download path (`release_fetch`). None are needed for
compute, but they live in the same crate as the rig.

**Path-shaped rig API.** The operations (`fit_mesh`, `apply_clip`, `bind_mesh`,
markers, `is_fitted`, ...) take and write `&Path` and use staged rename. On the
browser target the real API fails; minimal repro (Node-hosted
`wasm32-unknown-unknown`):

```text
fit_mesh("/x.glb", "/out.glb", ..) -> Err: cannot read /x.glb: operation not supported on this platform
```

`SkinnedClip::from_gltf(doc, buffers)` is already bytes-friendly (used by the
harness). Packs are also resolved from a directory on disk.

**Viewer.** Besides patches 1 and 2: `start_async_load` spawns `std::thread`
(compiles, cannot run on a no-thread wasm build; not exercised), writes a temp
file and re-reads it, and calls the path-based `glb_webp` converter. The
harness bypasses all of that with `bytes_ext`.

**Backend.** WebGL2 through `glow` (eframe web), keeping glow as the only
renderer as on desktop. WebGPU/`wgpu` was not tried.

**Event loop.** eframe web uses `requestAnimationFrame` instead of winit. The
desktop file-drag cursor workaround in `gui/src/dnd.rs` is not needed there
because browser drop events carry coordinates, and dropped files arrive as bytes
rather than paths. `rfd`, `open`, and `dirs` call sites need web equivalents.
Neither the rig nor the viewer uses `Instant`/`SystemTime`.

**Threads.** The build has no atomics/shared memory. In the Node-hosted
`wasm32-unknown-unknown` probe rayon degrades to a one-thread pool with no panic
(`par_iter ok ... current_num_threads=1`). The same check inside a browser is on
the checklist. Real multithreading needs `SharedArrayBuffer` (cross-origin
isolation headers) and an atomics build of std; not attempted.

**Design tension.** `VIEWER_ANIMATE.md` says not to stand up a second skinning
runtime. A GPU-skinning web path would contradict that; the CPU path above is
the one that was measured.

## Ordered extraction plan (preserve desktop behavior)

Every step must leave the native workspace building, `make ci` green, and the CLI
and desktop outputs unchanged. Compare against the existing golden fixtures, not
against bytes produced on another target.

0. **Gate: run the README checklist in a real browser.** Record browser, OS,
   GPU and the `gl` string. If WebGL2 IBL or the blit fails, fix or descope the
   viewer half before step 3. Steps 1-2 do not depend on it.
1. **Bytes API inside `asset-tap-core` (no new crate).** Add bytes-in/bytes-out
   forms of the rig operations (fit, rewrite, apply clips, marker seeding) and a
   pack source that can be bytes as well as a directory. Re-implement the path
   functions as thin wrappers that keep staging, validation and atomic rename.
   Add tests that path and bytes forms agree.
2. **`asset-tap-scene` crate.** Move the pure-compute rig files (canon,
   landmarks, body_fit, weights, skeleton, play, onmesh, export, write, pack
   catalog logic) behind that API. Dependencies: `glam`, `gltf`, `serde`,
   `thiserror`; `rayon` behind an optional `parallel` feature, on for native.
   Leave pack install, download, zip and `dirs` in core. Re-export from core so
   CLI, MCP and GUI import paths do not change. Gate: shim-style
   `wasm32-unknown-unknown` check in CI, and the 105 rig tests moved with the code.
3. **`asset-tap-viewer` crate.** Move `model.rs`, split into a renderer with no
   `eframe` dependency and a thin egui widget. Replace the temp-file loader with
   a bytes loader (retire the harness's duplicated texture-fix/bounds code) and
   keep a native path wrapper that does the thread and file read. Make the shared
   handle `Arc<Mutex<_>>` on native and a `SendWrapper` on wasm32 via `cfg`. Add a
   bytes variant of the WebP texture conversion.
4. **Web host.** Promote this harness to a small host crate or example; decide
   main-thread vs Web Worker loading after measuring decode cost.
5. **Optional, only if measured need:** threaded wasm for rayon, WebGPU.

## Risks and follow-ups

- Highest unknowns, all browser-side: IBL passes needing float render targets
  (`EXT_color_buffer_float`), the framebuffer blit via `intermediate_fbo`, texture
  decode time on the main thread for large GLBs, and tab memory limits.
- The stand-ins hide pack zip install, download and OS directories; step 2 must
  gate them properly rather than stub them.
- Unoptimized wasm is 10.4 MB (3.2 MB gzip); optimized size not measured.
- Toolchain: contributors need Rust 1.97 and a matching `wasm-bindgen-cli`
  (0.2.130 here); the sandbox system compiler was too old.
- The shim approach (include files by path) is a spike technique, not a design.
  It does prove the rig has no hidden dependency beyond the listed seams.
